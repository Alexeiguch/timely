# Expo remote reminders and channel ownership

2026-10-08. The owner selected Expo Push Service. Keep the existing local Expo notification scheduler; remote push fills eligible gaps in its seven-day/48-alert budget. Browser system Web Push remains outside the first release. Expo is a transport, not a scheduler: PostgreSQL holds durable jobs and an Inngest minute cron reconciles transactional task invalidation outbox rows, due jobs and receipts. A local-only script polls every 15 seconds for development. Hosted cadence, quotas and real delivery remain acceptance gates.

Both channels use shared recurrence/state/reminder planning and immutable device/occurrence/kind/version identities. An authenticated device first pauses its remote dispatch before altering OS schedules. It reports actual local mappings only after reconciliation succeeds and its clean sync cursor matches the server. The server recomputes every claimed identity and due instant, then enables dispatch for the uncovered plans. Local claims do not expire because a device goes offline. Elapsed local claims become handled; they never become a late remote retry. A crash during handoff leaves remote dispatch paused until the app reconciles.

The worker atomically claims pending jobs under the same owner lock used by sync mutations, rechecks current task/version, device permission, coverage and expiry, then sends outside the transaction. Jobs already dispatched or ambiguously accepted cannot be acquired by local scheduling. Native persists those remote-owned identities. If registration fails offline after a successful remote handoff, it keeps known local claims, allows newly authored offline versions locally and does not acquire competing schedules for canonical server-owned plans. Completing/editing on a disconnected device cannot recall a prior server send or another disconnected device's OS schedule; tap/foreground revalidate against current data.

Device registration checks the authenticated owner, registered platform, configured Expo project and unique token binding. Sign-out/unregister and account deletion cascade tokens/jobs through owner-scoped device rows. Payload routing uses the backend origin captured by the authenticated server during registration, not a client-supplied origin or the worker's current origin. Language is per device. Notifications contain authored title and timing copy, never notes; identifiers and tokens are not emitted by API responses or worker logs. Expo access tokens, APNs/FCM credentials and Inngest keys stay outside client bundles.

Only explicit rejection (HTTP 429 / MessageRateExceeded) allows bounded retry while the job is valid. A lost response, ambiguous acknowledgement, server error or interrupted dispatch becomes uncertain and is not automatically replayed. Receipt polling starts after 15 minutes; invalid-device receipts disable only the token used by that send, preserving a rotated replacement. Invalid credentials pause the affected device. The internal `delivered` status means Expo reports handoff to APNs/FCM, not proof that the user saw an alert. Exactly-once visible presentation is not guaranteed.
